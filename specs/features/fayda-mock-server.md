# Fayda mock server (dev OIDC provider)

**Status**: built and deployed by the API stack in dev (`faydaMode: 'mock'`). **Code**: `tools/fayda-mock/`. **Infra**: `infra/lib/constructs/fayda-mock-construct.ts`.

## What it is

A mock VeriFayda eSignet OpenID Connect provider. Dev points the WeredaConnect
server at it instead of real Fayda, so the national ID login flow can be tested
end to end without Fayda credentials. The server code path is identical for mock
and live: only the issuer URL, client ID and client secret change.

It is a Node.js Lambda behind a public Function URL. The Function URL root is the
issuer. Authorization codes and access tokens live in DynamoDB
(`${prefix}-fayda-mock-codes`, TTL on `expiresAt`). The RS256 signing key lives in
the SSM SecureString `/${prefix}/fayda-mock/signing-key`, generated by the Lambda
on its first cold start (CDK never sees the private key).

## Endpoints

| Method | Path | Behaviour |
|--------|------|-----------|
| GET | `/.well-known/openid-configuration` | Discovery (code flow, S256, RS256, `client_secret_post` + `private_key_jwt`, MOSIP acr values) |
| GET | `/.well-known/jwks.json` | Public key |
| GET | `/authorize` | Validates client, exact redirect URI, state, nonce, PKCE S256. Shows a test-user picker + OTP (`123456`) |
| POST | `/authorize/complete` | Issues a 5 minute single-use code, 302 to `redirect_uri?code&state` |
| POST | `/token` | Checks client auth, code (unused, unexpired, same redirect URI) and PKCE. Returns `id_token` (iss, sub, aud, exp, iat, nonce, name, given_name, family_name, phone_number, acr) + opaque `access_token` |
| GET | `/userinfo` | Same claims, Bearer access token |
| GET | `/health` | 200 |

A bad `client_id` or unregistered `redirect_uri` gets an HTML error page and is
never redirected. Other authorize errors redirect with `error=invalid_request`.

## Environment variables

Set by the construct: `CLIENT_ID` (`weredaconnect-${prefix}`), `CLIENT_SECRET`
(`dev-fayda-mock-secret`, a fixed mock value), `CODES_TABLE`, `SIGNING_KEY_PARAM`,
`ALLOWED_REDIRECT_URIS` (default `weredaconnect://fayda-callback`),
`REQUIRE_PKCE=true`, `FAYDA_MOCK=true`, and `ISSUER_URL_OVERRIDE` when given.
Optional: `CLIENT_JWKS_JSON` to enable `private_key_jwt`. Full table in
`tools/fayda-mock/README.md`.

## How dev is switched

1. Set `faydaMode: 'mock'` on the dev entry in `infra/lib/config/environments.ts`.
2. The API stack instantiates `FaydaMockConstruct` when `faydaMode === 'mock'` (never
   when `isProd`), writes its `issuerUrl` and `clientId` into the Fayda SSM parameters
   the server reads (`/{prefix}/fayda/issuer-url`, `/{prefix}/fayda/client-id`) and
   publishes the fixed client secret as `/{prefix}/fayda/client-secret-mock`. Both app
   redirects (`weredaconnect://fayda-callback`, `weredaconnect://fayda-link-callback`)
   are allowed, plus the web app callback page `/fayda-callback.html` on
   `dev-app.weredaconnect.com`, the temporary CloudFront origin and
   `http://localhost:8080` (browsers cannot open the deep link). The same list goes to
   the verify Lambda as `FAYDA_MOCK_WEB_REDIRECT_URIS` with `FAYDA_MOCK=true`; the
   server accepts web redirects only with that marker, so `faydaMode: 'live'` never
   does.
3. `faydaMode: 'live'` uses the real VeriFayda issuer and credentials. No server
   code change either way.

### Web app callback

`mobile/web/fayda-callback.html` loads in the tab the app opened for eSignet. Its
script (`fayda-callback.js`) posts the full callback URL on the same-origin
BroadcastChannel `wereda-fayda-callback`, strips the code from the address bar and
tries to close the tab. A reload (no query left) posts nothing, and the app ignores
any callback without a `state`, so a stray message cannot end or fail a wait. The app
tab (`core/auth/fayda_callback_links_web.dart`) feeds the URL into the same handler
the mobile deep link uses, which still checks `state`. On a live provider the start
call is refused and the web app treats Fayda as unavailable (verify later from the
mobile app).

Both relay files are unhashed, so `deploy-webapp.yml` and `scripts/deploy.sh` upload
them with `max-age=0, must-revalidate` instead of the one-year immutable cache.

The channel code has a browser-only test:
`cd mobile && flutter test --platform chrome test/core/auth/fayda_callback_links_web_test.dart`.

| FIN | Name | phone_number | Scenario |
|-----|------|--------------|----------|
| 1111111111111111 | Abebe Kebede | +251900100001 | Farmer |
| 2222222222222222 | Chaltu Tolosa | +251900100002 | Trucker |
| 3333333333333333 | Sara Haile | +251900100003 | Buyer |
| 4444444444444444 | Linked User | +251900100004 | Already linked (server decides) |
| 5555555555555555 | No Phone | none | Missing phone claim |

`sub` is a stable hash of the FIN, never the raw FIN.

Any other 16-digit FIN is a synthetic identity: stable name derived from the FIN,
no `phone_number` claim (so registration always goes through the SMS OTP). The
picker offers **Generate new identity** and **Type a FIN** for this; see
`tools/fayda-mock/README.md`. Use it to register fresh dev users, since each FIN
binds to one account (`FAYDA_004`).

## Maestro and failure modes

Append to the authorize URL:

- `auto=1&fin=<FIN>` skips the picker and redirects straight back with a code. `fin=new` uses a random FIN.
- `simulate=denied` redirects with `error=access_denied`.
- `simulate=down` returns 503.

## Production rule

The mock must never be deployed where `isProd` is true. The construct throws if
passed `isProd: true`, and the Lambda carries `FAYDA_MOCK=true` so the API stack's
`ProductionBypassGuard` can list it as a forbidden variable.
