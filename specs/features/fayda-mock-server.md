# Fayda mock server (dev OIDC provider)

**Status**: built and deployed by the API stack in dev (`faydaMode: 'mock'`). **Code**: `tools/fayda-mock/`. **Infra**: `infra/lib/constructs/fayda-mock-construct.ts`.

## What it is

A mock VeriFayda eSignet OpenID Connect provider. Dev points the WeredaConnect
server at it instead of real Fayda, so the national ID login flow can be tested
end to end without Fayda credentials. The server code path is identical for mock
and live: only the issuer URL, client ID and client private key change.

The mock copies the live provider's shape, checked against
`https://esignet.ida.fayda.et/v1/esignet/oidc/.well-known/openid-configuration`
(2026-09-29), so code that works against the mock works against Fayda:

- eSignet paths: the issuer is the host root, discovery, token, userinfo and JWKS
  live under `/v1/esignet`. The root `/.well-known/*` paths answer 404, as on Fayda.
- Fayda advertises `jwks_uri` as `/.well-known/jwks.json` and answers 404 there. The
  mock does the same, so the server's fallback to `/v1/esignet/oauth/.well-known/jwks.json`
  is exercised in dev.
- Client authentication is `private_key_jwt` (RS256) only. No client secret.
- The id_token carries identity only (`sub`, `acr`, `nonce`, `at_hash`, ...). Name and
  phone come from **userinfo**, returned as a signed JWT (`application/jwt`), and
  only for the claims the authorize request asks for in its `claims` parameter.

It is a Node.js Lambda behind a public Function URL. The Function URL root is the
issuer. Authorization codes and access tokens live in DynamoDB
(`${prefix}-fayda-mock-codes`, TTL on `expiresAt`). Two keys live in SSM
SecureStrings, each generated by the Lambda on first use (CDK never sees a private key):

| Parameter | What |
|-----------|------|
| `/${prefix}/fayda-mock/signing-key` | The mock's RS256 key for id_tokens and userinfo (mock only) |
| `/${prefix}/fayda/client-private-key` | The WeredaConnect relying party key, **the same parameter live mode uses**. Seeded as `PLACEHOLDER`; the mock replaces that with a generated base64 JWK on its first discovery or authorize call, checks client assertions with the public half, and the server signs with it. A usable key already there is kept |

## Endpoints

| Method | Path | Behaviour |
|--------|------|-----------|
| GET | `/v1/esignet/oidc/.well-known/openid-configuration` | Discovery, same fields as live Fayda |
| GET | `/v1/esignet/oauth/.well-known/jwks.json` | Public signing key |
| GET | `/authorize` | Validates client, exact redirect URI, state, nonce, PKCE S256, `claims` JSON. Shows a test-user picker + OTP (`123456`); a `login_hint` (`sub:<subject>` or `phone:<number>`, sent by the server in mock mode when an account verifies again) puts that identity first and preselected |
| POST | `/authorize/complete` | Mock only: issues a 5 minute single-use code, 302 to `redirect_uri?code&state` |
| POST | `/v1/esignet/oauth/v2/token` | `private_key_jwt` (iss = sub = client_id, aud = this URL, exp, single-use jti), then code (unused, unexpired, same redirect URI) and PKCE. Returns `id_token` + opaque `access_token` |
| GET | `/v1/esignet/oidc/userinfo` | Bearer access token. Signed JWT with `sub` plus the requested claims (`name`, `phone_number`, `individual_id`, `nationality`) |
| GET | `/health` | 200 |

A bad `client_id` or unregistered `redirect_uri` gets an HTML error page and is
never redirected. Other authorize errors redirect with `error=invalid_request`.

## Environment variables

Set by the construct: `CLIENT_ID` (`weredaconnect-${prefix}`), `CLIENT_KEY_PARAM`
(the RP key parameter above), `CODES_TABLE`, `SIGNING_KEY_PARAM`,
`ALLOWED_REDIRECT_URIS` (default `weredaconnect://fayda-callback`),
`REQUIRE_PKCE=true`, `FAYDA_MOCK=true`, and `ISSUER_URL_OVERRIDE` when given.
`CLIENT_JWKS_JSON` (a static RP public JWKS) replaces `CLIENT_KEY_PARAM` for local
runs and tests. Full table in `tools/fayda-mock/README.md`.

## How dev is switched

1. Set `faydaMode: 'mock'` on the dev entry in `infra/lib/config/environments.ts`.
2. The API stack instantiates `FaydaMockConstruct` when `faydaMode === 'mock'` (never
   when `isProd`), writes its `issuerUrl` and `clientId` into the Fayda SSM parameters
   the server reads (`/{prefix}/fayda/issuer-url`, `/{prefix}/fayda/client-id`) and
   gives the mock `CLIENT_KEY_PARAM=/{prefix}/fayda/client-private-key`, the parameter
   the verify Lambda already reads. Both app
   redirects (`weredaconnect://fayda-callback`, `weredaconnect://fayda-link-callback`)
   are allowed, plus the web app callback page `/fayda-callback.html` on
   `dev-app.weredaconnect.com`, the temporary CloudFront origin and
   `http://localhost:8080` (browsers cannot open the deep link). The same list goes to
   the verify Lambda as `FAYDA_MOCK_WEB_REDIRECT_URIS` with `FAYDA_MOCK=true`; the
   server accepts web redirects only with that marker, so `faydaMode: 'live'` never
   does.
3. `faydaMode: 'live'` uses the real VeriFayda issuer and credentials. No server
   code change either way; see the next section.

## Configuration: the same in mock and live mode

Fayda's sample relying party ([oidc-test-app](https://github.com/National-ID-Program-Ethiopia/oidc-test-app))
is configured with six variables. This is where each lives here. Mock and live
mode use the same parameter names, the same key format and the same verify Lambda
environment variables; only the values differ.

| oidc-test-app | WeredaConnect | Mock mode value | Live mode value |
|---------------|---------------|-----------------|-----------------|
| `CLIENT_ID` | `/{prefix}/fayda/client-id` (String, stack-owned) | `weredaconnect-{prefix}` | `faydaClientId` in `environments.ts` |
| `PRIVATE_KEY_BASE64` | `/{prefix}/fayda/client-private-key` (SecureString in dev/staging, Secrets Manager in prod) | generated by the mock | the key registered at partner.fayda.et |
| `TOKEN_ENDPOINT`, `USERINFO_ENDPOINT` | Discovered from `/{prefix}/fayda/issuer-url` (String, stack-owned), falling back to the eSignet paths | the mock's Function URL | `https://esignet.ida.fayda.et` (or `faydaIssuerUrl`) |
| `REDIRECT_URI` | Not a setting: the app sends `weredaconnect://fayda-callback` (registration) or `weredaconnect://fayda-link-callback` (link later), and the server accepts only those | both deep links, plus web callbacks in mock mode | the two deep links, registered at the portal |
| `CLIENT_ASSERTION_TYPE` | A constant in `FaydaOidcService` (RFC 7523 `jwt-bearer`) | same | same |

The issuer is the one value the sample lacks: the sample never validates the
id_token, while the server checks its signature, issuer, audience, expiry and nonce,
so it needs the issuer (and gets the endpoints from its discovery document).

Secrets follow `specs/decisions/secrets-backend-per-environment.md`: prod reads
Secrets Manager, dev and staging read an SSM SecureString to save the per-secret
cost (standard SecureStrings with the default `aws/ssm` key are free). The server
does not know which: `FAYDA_CLIENT_PRIVATE_KEY_ARN` carries either a Secrets
Manager ARN or a parameter name, and `AwsParameterResolver` routes on its shape.
The key is read uncached until it parses, so a key stored after a Lambda's cold
start is picked up without a redeploy.

## Switching to live Fayda

Only configuration changes. The server, mobile app and API contract stay the same.

**1. Register the client at [partner.fayda.et](https://partner.fayda.et)** (id.gov.et/api
redirects there). Submit:

- Redirect URIs: `weredaconnect://fayda-callback` and `weredaconnect://fayda-link-callback`.
- Client authentication `private_key_jwt`, with the public key from step 2.
- Claims: `name`, `phone_number` (userinfo). Ask for userinfo to be **signed, not
  encrypted**: the server refuses encrypted (JWE) userinfo and logs why.
- Auth factors (acr): the server asks for `mosip:idp:acr:generated-code` (OTP) and
  `mosip:idp:acr:biometrics`.

You get a `client_id`. Pricing, the approval time and whether a separate test
client exists are given during onboarding; there is no public anonymous sandbox.

**2. Create the key pair** (skip if the portal generates one and gives you a
base64 JWK; use that value as is in step 4):

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out fayda-rp.pem
# Public JWK to paste into the portal
node -e "const c=require('crypto');const k=c.createPublicKey(require('fs').readFileSync('fayda-rp.pem'));console.log(JSON.stringify({...k.export({format:'jwk'}),use:'sig',alg:'RS256'}))"
# Private key as one line (the seed script and --output text strip newlines)
base64 < fayda-rp.pem | tr -d '\n' > fayda-rp.b64
```

The server accepts the private key as PEM, JWK JSON, or base64 of either. Keep the
files out of the repo and delete them once stored.

**3. Point the environment at Fayda** in `infra/lib/config/environments.ts`:

```ts
faydaMode: 'live',
faydaClientId: '<client_id from the portal>',
// faydaIssuerUrl: only if Fayda gives you another host; default https://esignet.ida.fayda.et
```

**4. Store the private key** in the same parameter the mock used. Non-prod (SSM,
seeded as `PLACEHOLDER` by `scripts/seed-ssm-secrets.sh`; in dev it holds the
mock's generated key, which this overwrites):

```bash
aws ssm put-parameter --name /wereda-connect-<env>/fayda/client-private-key \
  --type SecureString --overwrite --value "$(cat fayda-rp.b64)" --region <region>
```

Prod (Secrets Manager, created by the stack with a random placeholder):

```bash
aws secretsmanager put-secret-value --secret-id /wereda-connect-prod/fayda/client-private-key \
  --secret-string "$(cat fayda-rp.b64)" --region me-south-1
```

**5. Deploy** (`/deploy` or merge to trigger `deploy-server.yml`). Deploying in live
mode removes the mock Lambda and its table; its signing key
(`/{prefix}/fayda-mock/signing-key`) is not stack-owned and can be deleted by hand.
A container that already parsed a client key keeps it, so replacing a working key
reaches new containers only (redeploy to force it).

**6. Check:**

```bash
curl -s https://esignet.ida.fayda.et/v1/esignet/oidc/.well-known/openid-configuration | head -c 300
```

Then register or link from the **mobile app** (a real phone with a Fayda identity).
The web app cannot use live Fayda: its https callback is registered with the mock only,
so on live it shows Fayda as unavailable. If the token call fails, the verify Lambda
logs `[FaydaOidc]` lines: a missing or unreadable key, a discovery issuer mismatch, or
encrypted userinfo.

**Rollback:** set `faydaMode: 'mock'` again and deploy.

### Web app callback

`mobile/web/fayda-callback.html` loads in the tab the app opened for eSignet. Its
script (`fayda-callback.js`) posts the full callback URL on the same-origin
BroadcastChannel `wereda-fayda-callback`, strips the code from the address bar and
tries to close the tab. A reload (no query left) posts nothing, and the app ignores
any callback without a `state`, so a stray message cannot end or fail a wait. The app
tab (`core/auth/fayda_callback_links_web.dart`) feeds the URL into the same handler
the mobile deep link uses, which still checks `state`. On a live provider the start
call is refused and the web app treats Fayda as unavailable (verify later from the
mobile app).

Both relay files are unhashed, so `deploy-webapp.yml` and `scripts/deploy.sh` upload
them with `max-age=0, must-revalidate` instead of the one-year immutable cache.

The channel code has a browser-only test:
`cd mobile && flutter test --platform chrome test/core/auth/fayda_callback_links_web_test.dart`.

## Test users

| FIN | Name | phone_number | Scenario |
|-----|------|--------------|----------|
| 1111111111111111 | Abebe Kebede | +251900100001 | Farmer |
| 2222222222222222 | Chaltu Tolosa | +251900100002 | Trucker |
| 3333333333333333 | Sara Haile | +251900100003 | Buyer |
| 4444444444444444 | Linked User | +251900100004 | Already linked (server decides) |
| 5555555555555555 | No Phone | none | Missing phone claim |

`sub` is a stable hash of the FIN, never the raw FIN.

**Identity for my phone number** (picker option, or `auto=1&phone=<number>`): the Fayda
record of that phone. A seeded phone returns its seeded user; any other Ethiopian mobile
number gets a synthetic person with a FIN derived from the phone and the `phone_number`
claim set (in userinfo), so the same phone is always the same person. `POST /user/fayda-link`
accepts only the account owner (same Fayda ID, else matching phone), so a generated or
typed identity (no phone) fails with `FAYDA_007` on an unlinked account, and any other
person's identity with `FAYDA_005` on a linked one.

Any other 16-digit FIN is a synthetic identity: stable name derived from the FIN,
no `phone_number` claim (so registration always goes through the SMS OTP). The
picker offers **Generate new identity** and **Type a FIN** for this; see
`tools/fayda-mock/README.md`. Use it to register fresh dev users, since each FIN
binds to one account (`FAYDA_004`).

**Continue as ...** (the identity on the account): a generated FIN is never shown and
the server stores only its subject, so no picker choice could reproduce that identity
when the account verifies again (payment above 10,000 ETB, profile, KYC prompt). In mock
mode (`FAYDA_MOCK=true`) `POST /user/fayda-start` therefore puts a `login_hint` on the
authorize URL: `sub:<the account's Fayda ID>`, or `phone:<the account phone>` while it
holds none. The picker shows that identity first and preselected and signs in as exactly
that subject (a seeded subject gives the seeded person; any other is honoured as a sub-only
identity with a stable synthetic name, no phone, no `individual_id`). A `phone:` hint
preselects **Identity for my phone number** with the number filled in. The hint is advice
only: the link still refuses any identity that is not the account's own. Live Fayda never
receives it (`specs/contracts/auth-api.md` 2.12.1).

## Maestro and failure modes

Append to the authorize URL:

- `auto=1&fin=<FIN>` skips the picker and redirects straight back with a code. `fin=new` uses a random FIN.
- `auto=1&phone=<number>` does the same as that phone's owner (with the `phone_number` claim).
- `auto=1&fin=hint` signs in as the identity the URL's `login_hint` names (the account's own); without a usable hint it redirects with `error=invalid_request`.
- `simulate=denied` redirects with `error=access_denied`.
- `simulate=down` returns 503.

## Production rule

The mock must never be deployed where `isProd` is true. The construct throws if
passed `isProd: true`, and the Lambda carries `FAYDA_MOCK=true` so the API stack's
`ProductionBypassGuard` can list it as a forbidden variable.
