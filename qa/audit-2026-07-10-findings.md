### 1. [CRITICAL] Delivery status transitions send POST-increment version → every server transition conflicts and reverts (escrow never releases)

- **File:** `mobile/lib/features/delivery_verification/data/repositories/delivery_repository.dart:441`
- **Area:** mob-delivery
- **Detail:** confirmPickup increments the delivery version inside the Isar txn (line 433 `delivery.version += 1`) and then sends that SAME post-increment value to the server as `'version': delivery.version` (line 441). The server's delivery-update path parses `data.version` as `:expectedVersion` and enforces `ConditionExpression = "#v = :expectedVersion"`, storing `clientVersion + 1` on success (server/src/Functions/SyncFunction.cs:3880-3884, 3901, 4016) — i.e. the client must send the version it currently holds on the server (PRE-increment). A delivery is created with server version=1 and local version=1 (create forces version="1", SyncFunction.cs ~3162), so the first pickup sends version=2 while the server still holds 1 → ConditionalCheckFailedException → the op returns status:"conflict" and pickedUp is never applied; ConflictResolver._resolveDelivery (mobile/lib/core/sync/conflict_resolver.dart) then applies server-wins and reverts the local status back to pending. The identical post-increment bug repeats in confirmDelivery (line 504), markInTransit (line 565), raiseDispute (line 615) and cancelDelivery (line 654), so NO delivery status transition ever commits server-side: trucker pickup, buyer delivery-confirmation, and therefore escrow release to the farmer all silently fail and roll back. This is the exact off-by-one already fixed for trips (trip_listing_repository.dart:302-320 captures baseVersion and sends it) and orders, but delivery was never fixed. Violates specs/contracts/sync-protocol.md optimistic concurrency, delivery-verification-api.md, and CLAUDE.md 'core marketplace flow must never break'.
- **Verifier (refutation attempt failed):** Delivery status transitions send the POST-increment version (line 441 sends delivery.version after line 433 does version += 1), but the server delivery-update path (SyncFunction.cs:3881-3901, 4016) requires the client to send the version it currently holds (expectedVersion = sent version; stores clientVersion+1).
